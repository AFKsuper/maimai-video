# 手机渲染部署与使用指南

本文档描述如何把「谱面确认」升级为**手机 60fps 硬件编码、服务器只做转发**的架构。

---

## 一、这套东西是怎么工作的

本项目当前部署形态是**云服务器 + 手机移动网络**，两者不在同一个局域网，也**不需要**。

```
                        ┌──────────────────────────────────────────┐
   QQ 群                │  云服务器 HoshinoBot（阿里云，公网 IP）      │
  ┌────────┐            │  8081  QQ 反向 WS                         │
  │ 谱面确认 │──────────▶│  8778  手机通信桥（aiohttp，0.0.0.0）      │
  └────────┘            │        ▲ 公网可达（安全组需放行 8778）      │
                        └────────┼─────────────────────────────────┘
                                 │ ① 命令入队        ④ 要发群时才取视频
                                 │                    （/video/{name}）
                        ┌────────┴─────────────────────────────────┐
                        │  手机（Termux + Chrome，WiFi 或 4G 都行）  │
                        │                                          │
                        │  render_server.py  ── 8777 渲染页         │
                        │                    ├─ 8780 落盘（loopback）│
                        │                    └─ /audio/ 音轨代理     │
                        │                                          │
                        │  Chrome worker.html（打开一次，常驻）      │
                        │   ② 每 3 秒 GET 公网 8778/api/task 领任务  │
                        │   ③ 取音轨（本机 8777 代理 → 上游 mp3）    │
                        │   ④ Worker 内 WebCodecs 逐帧编码 + AAC 音轨│
                        │      → POST 127.0.0.1:8780/save          │
                        │        ↘ 落盘 /sdcard/Download/maimai/   │
                        │      → POST 公网 8778/api/stored 记账     │
                        └──────────────────────────────────────────┘
```

**关键点：所有跨网通信都是手机主动发起的出站连接。** 服务器从不主动连手机，
因此手机在 NAT 后面、用 WiFi 还是 4G、IP 会不会变，全都不影响。

> 手机连家庭 WiFi 时，上传走的是局域网（实测 WiFi 6 / 229 Mbps），
> 不消耗手机流量；只有在外用 4G 时才走流量。传一支 720p/90 秒的成品
> 大约 18 MB，一百多支也就 2 GB 出头。

**核心思路**：手机的成品**先存在手机自己身上**，服务器只在有人要的时候才取一趟。

- 渲染出的 MP4 直接写进手机存储（`/sdcard/Download/maimai/`），**一个字节都不经过服务器**。
- 服务器只收一条「这支有了」的通知（几百字节的元数据），不存视频。
- 群里点播时，服务器让手机 Agent 把这支传上来 —— 只在需要发群时传，传完留着复用。
- 服务器缓存超过 **1 GB** 就按「最久没被用过」淘汰（`MP4_CACHE_MAX_MB`）。
  淘汰不丢任何东西 —— 权威副本永远在手机上，下次要再传一趟而已。

> 为什么不直接把成品 POST 给服务器、再让手机拉回去？
> 那样同一份字节要在 WiFi 上走两遍（手机→服务器发群、服务器→手机归档），
> 曲目一多服务器还得跟着存几百 GB。现在只在发群那一趟走一次。

**手机渲染出来的成品自带音轨，服务器只负责兜底。**

> 手机那条链路是「主线程解码 mp3 → Worker 里编 AAC → 和画面一起 mux 进 MP4」：
> 1. 服务器把任务发下来时会带上 `audio=` 参数（音轨的真实地址）；
> 2. 工作页拿这个地址向手机本机的 `127.0.0.1:8777/audio/<id>.mp3` 要数据，
>    `render_server.py` 代下载并缓存到 `/sdcard/Download/maimai_audio/`，
>    然后交给主线程的 `OfflineAudioContext.decodeAudioData` 解成 PCM；
> 3. PCM 递给 Worker，用 `AudioEncoder` 编成 AAC 128k，
>    和视频轨一起写进同一个 MP4。
>
> 为什么要绕一个本机代理：音轨源站 `astrodx-charts.saop.cc` 没有开 CORS，
> 页面直连 `fetch` 会被浏览器拦死（实测 `TypeError: Failed to fetch`）；
> 同一个 URL 用 `curl` 则是 200。绕同源代理是最省事的解法。
> 也不能让手机自己猜 URL —— 音轨在 `astrodx-charts.saop.cc/<分片>/<id>/track.mp3`，
> 那个分片号只有 `catalog.json` 知道，所以必须由服务器随任务下发。

> 服务器侧还有一层兜底（`audio_mux.py`）：万一手机端没编出音轨（音轨下载失败、
> 老版本页面、或排队时刚好没网），服务器入库时会用 ffmpeg 补一条，
> 用 `-c:v copy` 透传画面，**不重编码、不损画质、帧数一模一样**。
> 已经有音轨的成品会被识别出来直接跳过，不会重复补。
> 音轨也缓存在服务器 `cache/audio/<曲id>.mp3`，同一首反复点播只下一次。
> 兜底失败（没网、源站挂了）**不影响发群** —— 只是这一支没声音，视频照常出。
> 关掉兜底：`config.py` 里 `PHONE_AUDIO_MUX_ENABLED = False`。

**手机端为什么需要一个小服务（8780）**：浏览器没法自己写进 `Download/` 目录 ——
`a[download]` 没有用户手势不生效（无人值守的批量场景根本点不了），
OPFS 又躺在 Chrome 私有沙箱里，Termux 和文件管理器都看不见。
所以 Termux 里跑一个 `render_server.py`，它同时提供两个回环服务：
`127.0.0.1:8777` 渲染页 + `127.0.0.1:8780` 落盘。

> **服务器不在局域网，8780 还有用吗？** 有。8780 只监听手机自己的 `127.0.0.1`，
> 云服务器永远连不进去，也**不需要**连。它服务的是「浏览器 → 手机磁盘」这一段，
> 全程不出手机。跨网的那一段是手机主动 `POST` 到公网 `8778/api/stored`，
> 方向是手机→服务器，同样不需要反向隧道。
> 换句话说：**服务器的地理位置与 8780 完全无关**，换成什么云、在哪个国家都一样。

**手机浏览器里的 `worker.html` 主动去服务器「要活干」**，而不是服务器去命令手机打开网页。

> 为什么不用「服务器命令手机打开网页」？
> Android 10 以后，系统禁止后台应用启动界面。Termux 里执行 `am start` 会被拦下，
> 实测报 `java.lang.reflect.InvocationTargetException`（退出码 1）。
> 让网页自己轮询，则完全不依赖任何后台启动能力。

**编码为什么必须跑在 Web Worker 里**：主线程页面一旦进入后台，Chrome 会重度节流，
编码精确冻结在第 5431 帧（`encodeQueueSize` 恒定不再变化）；同样的编码逻辑放进
Worker，页面全程 hidden 也能跑完。实测 11879 全曲 9850 帧 / 52 MB / 94 秒（比实时快
约 1.7 倍），整个过程手机屏幕是关着的。这是「打开一次就不用管」的地基。

> 前提：手机 Chrome 必须停在 `http://127.0.0.1:8777/worker.html`（由手机本机的 render_server.py 提供），
> 因为只有 localhost 才是安全上下文，走局域网 IP 或公网 IP 时浏览器都不提供 `VideoEncoder`。
> 页面本身可以切后台、可以锁屏，但**别把这个标签页关掉或划走**。

## 二、首次部署（4 步）

> 这里写的是**云服务器 + 手机移动网络**的实际部署方式，不需要 USB、不需要 `adb reverse`、
> 不需要和服务器处在同一个网络里。手机只要自己能上网就行。

### 第 1 步：启动机器人（云服务器上）

```powershell
cd "C:\Users\Administrator\Desktop\HoshinoBot"
py -3.10 run.py
```

看到以下日志即为正常：

```
mai_preview 手机通信网关启动: True
mai_preview 渲染静态服务就绪（手机访问 8777）
```

> 8081（QQ）与 8778（手机桥）跑在 `run.py` 这个进程里。
> 老版本日志里的「渲染静态服务就绪（手机访问 8777）」在云服务器部署下**没有用**——
> 8777 现在由手机本机的 `render_server.py` 提供，服务器不再托管渲染页。

启动后在服务器上验证：

```powershell
curl http://127.0.0.1:8778/healthz
# {"status":"ok","service":"mai_preview_phone_bridge","online":false,"online_count":0}
```

**再从公网验证一次**（这一步最关键，能验证安全组是否放行）：

```powershell
curl http://YOUR_SERVER_HOST:8778/healthz
```

> 如果本机 127.0.0.1 通、公网 IP 不通，就是**云厂商安全组没放行 8778**
> （Windows 防火墙不用管，实测三个 profile 全关）。到阿里云控制台
> 「实例 → 安全组 → 配置规则 → 入方向」加一条 `TCP:8778`，源可以是 `0.0.0.0/0`
> 或你手机的出口 IP。放行后手机侧会自动重连，不需要重启任何进程。

### 第 2 步：手机装 Termux 并启动渲染 + 落盘服务

在手机 Termux 里执行：

```bash
bash /sdcard/Download/start_render.sh
```

> 首次部署要先把 `phone_client/` 下的 `render_server.py`、`start_render.sh`、
> `web/` 四个文件推到手机对应位置，见 `phone_client/README_TERMUX.md`。
> 确认 `render_server.py` 会读到 `config.json` 里的 `server_host`
> （日志里会有 `[notify] 桥接地址取自 ...: http://YOUR_SERVER_HOST:8778`）——
> 读到这一行，落盘后的 `/api/stored` 上报才会生效。

自检：

```bash
curl http://127.0.0.1:8777/healthz    # 渲染页
curl http://127.0.0.1:8780/health     # 落盘服务
```

> 这两个都是手机回环地址，**只有手机自己能访问**，服务器连不进去也不需要连。

### 第 3 步：在手机 Chrome 里打开常驻工作页

地址里的 `bridge` 要写成**服务器的公网地址**：

```
http://127.0.0.1:8777/worker.html?bridge=http%3A%2F%2FYOUR_SERVER_HOST%3A8778&token=YOUR_SECRET_TOKEN&px=720&fps=60&bitrate=4000000
```

> 也可以让机器人直接把这个链接发给你：手机节点不在线时，它会回 `手机节点还没上线，两步启动：…`，
> 第 1 条就是这个链接；手机在线但没预录、工作页也没跑时，它会回
> `手机没有这条的预录视频，也检测不到渲染工作页在跑。…`，链接同样在回复里。

> **为什么页面必须用 `127.0.0.1`，而 `bridge` 却要写公网 IP？**
> 这两者约束不同：
> - **渲染页（8777）**：浏览器只在**安全上下文**（HTTPS 或 localhost）下才暴露 `VideoEncoder`。
>   走任何非 localhost 地址（局域网 IP、公网 IP）时 `VideoEncoder` 都是 `undefined`，编码必然失败；
>   走 `http://127.0.0.1:8777` 时 `isSecureContext === true`。
> - **桥接口（8778，取任务 + 上报）**：没有安全上下文要求，手机出站访问服务器公网 IP 即可。

> **如果你还想用 Termux Agent（预录视频秒回）**：`phone_client/phone_agent.py` 在仓库里是以
> `phone_agent.py.b64` 形式存放的，拷到手机后**必须先还原**才能跑——
> 在 `phone_client` 目录里执行 `base64 -d phone_agent.py.b64 > phone_agent.py`
> （原因：火绒 HIPS 会按文件内容删掉含 `am start` + `android.intent.action.VIEW` 组合的 `.py`）。
> 完整步骤见 `phone_client/README_TERMUX.md` 第四步。

> **⚠ 落盘服务由 `render_server.py` 一并提供（不再单独起 `save_server.py`）**：
> 手机渲染出的 MP4 要写进 `/sdcard/Download/maimai/`，而浏览器自己写不进去
> （`a[download]` 没手势不生效，OPFS 又在 Chrome 沙箱里）。
> `render_server.py` 同时监听两个回环端口：`8777`（渲染页）与 `8780`（落盘）。
> 所以第 2 步那一条 `bash /sdcard/Download/start_render.sh` 就把两件事都起了。
> 验证：`curl http://127.0.0.1:8780/health` 返回 `{"ok": true, ...}` 就算好了。
> 旧的 `save_server.py` / `start_save.sh` 已被接管，**不需要再单独跑**。
> **手机重启后要重新起一次**：`bash /sdcard/Download/start_render.sh`。
> 不起这个服务，渲染仍能跑完，但成品存不进手机 —— 页面日志会显示「保存失败」。

打开后页面应显示：

| 项 | 正常值 |
|---|---|
| 状态 | 在线待命 |
| 编码位置 | Worker（不受后台节流） |
| 屏幕常亮 | 已开启 |
| 版本 | worker-3 |
| 落盘地址 | `http://127.0.0.1:8780/save` |

页面顶部会打印 `安全上下文已确认，WebCodecs 可用`，这句话是判断环境是否正确的关键。

**打开一次就行，之后可以切到别的应用、可以锁屏。** 编码在 Web Worker 里跑，不受
页面可见性影响。只要别把这个标签页关掉/划掉即可。建议加个书签，方便以后重开。

### 第 4 步：验证链路（服务器侧）

```powershell
curl "http://127.0.0.1:8778/status?token=YOUR_SECRET_TOKEN"
```

看到 `worker.alive` 为 `true` 就说明手机工作页已连上：

```json
{
  "status": "ok",
  "online_phones": 0,
  "worker": {"alive": true, "last_seen_s": 1.7, "ua": "Mozilla/5.0 (Linux; Android 13; Mi 10 Pro ...) Chrome/143..."},
  "render_queue": {"pending": 0, "tasks": []},
  "cached_videos_count": 3,
  "cached_videos": [{"name": "11879_5.mp4", "size": 54727166}]
}
```

### 验收：在群里试一条

```
谱面确认 11879 紫
```

按当时状态不同，群里会看到下面几种回复。**以下文案与 `mai_preview.py` 里的 `bot.send(...)` 字符串逐字一致**：

**A. 服务器缓存已有成品**（秒回，只发一条）：

```text
【视频】《曲名》 · 曲id 11879 · 紫 MASTER Lv.14.9
服务器缓存命中，直接发成品。
谱面数据来自「ADX 谱面资源」https://adxdls.saop.cc/charts/11879?preview=1 （CC BY 4.0）
```

（没写难度时第一行末尾会多一句 `（没写难度，取的最高）`。视频先按 `file:///` 直发，失败自动换 base64 重发；两次都失败才发文字 `视频没发出去（协议端可能不支持直发视频）。` + 曲目信息 + 本地文件路径。）

**B. 手机 Agent 在线、预录库里有成品**（两步）：

1. `服务器没有缓存，正在向手机调预录视频…`
2. 【视频】+ A 的三行说明（第 2 行换成 `手机节点 60fps 编码完成。`）

**C. 手机在线但没预录、工作页在跑**（转现场渲染，约 1-2 分钟）：

1. `服务器没有缓存，正在向手机调预录视频…`
2. `手机没预录这条，转现场渲染：由手机工作页现场编码 60fps 原视频，约 1-2 分钟。编码跑在后台 Worker 里，手机可以锁屏或切到别的应用。`
3. 【视频】+ 三行说明（`手机节点 60fps 编码完成。`）

**D. 手机节点都不在线**（只发文字，不发视频）：

```text
手机节点还没上线，两步启动：
1. 手机 Chrome 打开工作页（打开一次就行，之后可以切后台）：<工作页地址>
2. 或在 Termux 跑起 agent 脚本，回传手机上已预录的视频
```

其余失败情形的原文见「五、故障排查」末尾的**失败文案速查**表。

## 三、日常使用

### 命令一览

现在**只有一条命令**（外加一条帮助）：

| 命令 | 说明 |
|---|---|
| `谱面确认 <曲id或别名>` | 发**该曲最高难度档**（有白发白、没白发紫、宴谱发宴） |
| `谱面确认 <曲id或别名> <难度>` | 发指定难度 |
| `帮助mai_preview` | 回发帮助原文（`sv_help` 全文）+ 署名行 |

难度词（`render_core.parse_diff` 实际识别的写法，大小写不敏感）：

| 写法 | 槽位 | 颜色 |
|---|---|---|
| `1` `绿` `Basic` `简单` | 2 | 绿 |
| `2` `黄` `Advanced` `进阶` `普通` | 3 | 黄 |
| `3` `红` `Expert` `困难` | 4 | 红 |
| `4` `紫` `Master` `大师` | 5 | 紫 |
| `5` `白` `Re:Master` `re` `rem` `remaster` | 6 | 白 |
| `宴` `Utage` `双押` | 7 | 宴 |

**数字 1–5 是「第几档」**，不是 simai 的槽位号（槽位号 2–7 只出现在磁盘文件名里，
用户不用记）。`6` / `7` 仍按旧槽位直通，老用户写惯了不会断。

不写难度时取该曲**最高难度档**：有白谱发白谱、没白谱发紫谱、宴谱发宴谱。
按槽位号取最大而不是按定数比 —— 官方定数并不总随难度递增，全库有 9 首白谱定数
略低于紫谱（例 11232 紫 13.8 / 白 13.7），按定数取会把这些曲子发成紫谱，
与「最高档」的直觉相反。回复第一行会带一句 `（没写难度，取的最高）`。
输入里夹带的 `原视频`、`视频`、`mp4` 词缀会被自动忽略，它们**不是**独立命令。

> 更早版本里的旧别名命令已全部删除，现在只认上表这两条；老用户发旧命令不会收到任何响应。

### 三种响应速度

| 情况 | 耗时 | 群里会看到 |
|---|---|---|
| 服务器缓存已存在 | **1 秒内** | `服务器缓存命中，直接发成品。` |
| 手机预录库里有成品 | 数秒 | 先 `服务器没有缓存，正在向手机调预录视频…`，随后 `手机节点 60fps 编码完成。` |
| 都没有，手机现场编码 | **约 1–2 分钟** | `手机没预录这条，转现场渲染：由手机工作页现场编码 60fps 原视频，约 1-2 分钟。编码跑在后台 Worker 里，手机可以锁屏或切到别的应用。` |

### 关于重复请求

同一首曲子如果被多个群同时请求，**只会渲染一次**，成品发给所有等待的群。
渲染队列会自动去重，不必担心重复触发。

### 机器人重启后要做什么

**什么都不用做。** 手机上的 `worker.html` 会自己重试重连（实测 1.5 秒内恢复），
已经渲染好的缓存也不会丢。只要：

1. 手机 Chrome 还开着 `worker.html`（不用管之前连没连上）
2. 手机的 `render_server.py` 还在跑（8777 + 8780）

> 因为所有跨网连接都是手机主动出站，**服务器重启后手机不需要做任何操作**，
> 连 8778 的轮询会自动重连。这一点和「必须重新执行 adb reverse」的旧架构完全不同。

> **注意：渲染队列是内存中的，重启会清空。**
> 重启瞬间正排在队里等待渲染的请求会丢失，那些群会一直等到超时（约 15 分钟）才收到失败提示。
> 实际影响很小——正常使用中队列几乎是空的（拿到任务就立即派发给手机），
> 只有恰好卡在「机器人重启 + 排队中」这个瞬间才会遇到。重新发一次命令即可。

## 四、常用维护命令

以下都在**云服务器上**执行：

```powershell
# 本机自检（不经过公网）
curl "http://127.0.0.1:8778/healthz"

# 查看服务状态（含手机工作页存活、渲染队列、手机已存数量、缓存清单）
curl "http://YOUR_SERVER_HOST:8778/status?token=YOUR_SECRET_TOKEN"

# 查看某个谱面的渲染产物信息（把文件名换成 cache/mp4 下实际存在的那个）
ffprobe -v error -select_streams v:0 -show_entries stream=codec_name,width,height,r_frame_rate,nb_frames -show_entries format=duration,size -of default=noprint_wrappers=1 "C:\Users\Administrator\Desktop\HoshinoBot\hoshino\modules\mai_preview\cache\mp4\220_5.mp4"

# 手动触发一次渲染（调试用，会阻塞到完成；注意客户端自身超时要放大）
curl "http://YOUR_SERVER_HOST:8778/debug/render?chart_id=220&diff=5&timeout=400&token=YOUR_SECRET_TOKEN"

# 把某支成品从服务器缓存取回本地核对（模拟发群时的那一趟）
curl -o 220_5.mp4 "http://YOUR_SERVER_HOST:8778/video/220_5.mp4?token=YOUR_SECRET_TOKEN"
```

> `/status`、`/video/*`、`/debug/*` 都必须带 `token`，否则返回 403
> `{"status":"error","message":"unauthorized"}`。
> token 可放 query（`?token=`）、`X-Token` 头或 `Authorization: Bearer`。

### 缓存目录

```
服务器：hoshino\modules\mai_preview\cache\mp4\<曲目ID>_<难度槽位>.mp4
        hoshino\modules\mai_preview\cache\audio\<曲目ID>.mp3      ← 兜底补轨用
手机：  /sdcard/Download/maimai\<曲目ID>_<难度槽位>.mp4            ← 权威副本
        /sdcard/Download/maimai_audio\<曲目ID>.mp3                ← 手机编音轨用
        /sdcard/Download/maimai_charts\<曲目ID>.txt               ← 谱面缓存
例：220_5.mp4  = 曲目 220 的 紫(Master) 难度
    220.mp3    = 曲目 220 的音轨
```

服务器 `cache\audio\` 和手机 `maimai_audio\` 里的音轨都是只增不减 ——
一首曲子通常几 MB，全库也就几 GB，而且同一首会被不同难度反复用到，
删了反而要重新下载。手动清理可以直接删目录，下次入口请求时会自动重下。

难度槽位只认 **2-7**（2=绿 3=黄 4=红 5=紫 6=白 7=宴）。这个白名单写死在
`phone_bridge.py` 的 `_VALID_DIFF_SLOTS`，`0/1/8/99` 之类会被当非法难度直接拒收
（返回 422，报的是 `missing_ids`，日志里看不出是难度而非 ID 的问题）。
所以手动往 `cache/mp4/` 里放文件时，文件名里的槽位必须是 2-7，否则查不到。

> 注意区分两套数字：**文件名里的 2-7 是 simai 槽位号**，
> **群里敲的 1-5 是「第几档」**。用户写 `4` 会被 `parse_diff` 翻成槽位 5，
> 落盘成 `xxx_5.mp4`。这是有意为之 —— 让用户数「第几档」比记槽位号直观。
若将来 simai 真出现 8+ 槽位，要同时改 4 处：`phone_bridge._VALID_DIFF_SLOTS`、
`render_core.DIFF_ALIASES`、`alias_resolve.SLOT_COLOR`、`serve.py` 的 `SLOT_NAME`。

### ⚠ 难度校验只有一道，且它拦不住「难度发错」

这一点必须知道，否则很容易误判线上问题。

服务器的 `video_verify` 用 catalog 里的 `duration_ms` 校验回传视频，
阈值是比值落在 **0.75–1.35** 之外才拒收。但**同一首歌各难度的时长几乎一样**，
用全量 catalog 算过：22710 组「请求 A 难度、实际回 B 难度」的组合里，
**0 组能被这条时长闸门拦下（0.0%）** —— 因为同曲各难度时长普遍只差几百毫秒：

| 曲目 | 各难度时长 | 说明 |
|---|---|---|
| 11879《Xaleid◆scopiX (2)》 | 2/3/4/5 全是 `162499ms` | 四个难度**完全相同**，比值恒等于 1.0 |
| 11422《11422》 | 2=`129231` 3=`132462` 4=`132000` 5=`129462` | 极差约 2.5%，比值都在 0.98–1.02 |
| 12059《天靈靈地靈靈》 | 4=`144000` 5=`144677` | 差 0.5% |

全库统计：1780 首可比对的曲目里，**296 首（16%）各难度时长完全一致**，
1484 首（84%）有差异但差异远小于闸门阈值。

**结论：难度正确性只能靠手机端 Agent 的文件名精确匹配来保证，
不能指望服务器事后用时长兜住。** 之前 Agent 的 `find_video` 用子串匹配，
请求红谱(4)而手机只有紫谱(5)时会把紫的成片发出去，服务器时长校验照样放行，
用户静默拿到错难度的视频。该缺陷已修（改成严格 `<曲目ID>_<难度>` 解析，
匹配不上就回「没预录」让服务器转现场渲染）。

> 若要让服务器也具备难度自检能力，需要额外回传难度标识（例如在
> `/upload` 的 query 里带上 `slot`，并在校验时比对），当前版本没有做。


一个 720p/60fps 全曲 MP4 约 **30–55 MB**。缓存可以随时清空，重新请求即可重建。

### 成品直接落手机（服务器只当发群时的中转站）

**为什么这样设计**：手机 Chrome 渲染出的 MP4 如果先 `POST` 到服务器、再让手机拉回去归档，
同一份字节要在 WiFi 上走两遍，曲目一多服务器还得跟着存几百 GB。
现在改成**渲染完直接写进手机存储**，服务器只在有人点播要发群时才取一趟。

完整闭环：

```
手机 Worker 编码完成
      │
      ├─ POST 127.0.0.1:8780/save  （loopback，不出手机）
      │        ▼
      │   /sdcard/Download/maimai/<曲id>_<难度>.mp4
      │        ▼
      └─ POST http://YOUR_SERVER_HOST:8778/api/stored 通知服务器（只带元数据）
               ▼
          服务器记一条「这支在手机上」的索引
               │
               ▼
   群里点播：服务器没有 → 让手机 Agent 传上来 → 落 cache/mp4/ → 发群
               │
               ▼
          留在服务器缓存里复用，超过 1 GB 按最久未用淘汰
```

关键设计点：

- **手机端为什么要有落盘服务（8780）**：浏览器写不进 `Download/` 目录。
  `a[download]` 没有用户手势不生效（实测无人值守时点了也不落盘），
  OPFS 是 Chrome 私有沙箱，Termux 和文件管理器都看不见。
  所以在 Termux 里跑 `render_server.py`，由它在本机 `127.0.0.1:8780` 收字节并落盘。
- **`/api/stored` 只收元数据**，不收视频字节。视频已经在手机上了，
  这个端点只记账 + 唤醒等结果的请求。真正的字节回传仍走 `/upload`（会跑 ffprobe 时长校验）。
- **服务器缓存只留最近用过的**：`MP4_CACHE_MAX_MB` 默认 1024（1 GB），
  超出就按文件 mtime（命中时会刷新）淘汰最久没用过的那批。
  淘汰不丢数据 —— 手机上有权威副本，下次要会再传一趟。
- **投递中的文件不会被淘汰**：`evict_cache_lru(keep=...)` 会跳过正在发的那支，
  避免和 QQ 协议端读 `file:///` 抢时间。

相关开关（`config.py`）：

| 配置 | 默认 | 作用 |
|---|---|---|
| `PHONE_SAVE_URL` | `http://127.0.0.1:8780/save` | 下发给手机的落盘地址（手机本机回环） |
| `MP4_CACHE_MAX_MB` | `1024` | 服务器 MP4 缓存上限（MB），0 = 不限制 |
| `PHONE_STORE_ENABLED` | `True` | 关掉则不做手机侧的成品记账 |
| `PHONE_STORE_DIR` | `/sdcard/Download/maimai` | 手机上成品存放目录 |
| `PHONE_STORE_TIMEOUT_S` | `300` | 查询手机目录的超时（秒） |
| `PHONE_RENDER_TIMEOUT_S` | `900` | 单支现场渲染的最长等待（秒） |

> **手机 `render_server.py` 必须开着**。它是 Termux 里的独立进程，随 Termux 一起被杀。
> 云服务器重启、掉线都不影响它；但手机重启后要手动起一次：
> ```bash
> bash /sdcard/Download/start_render.sh
> ```
> 用 `curl http://127.0.0.1:8780/health` 确认，返回 `{"ok": true, ...}` 就是好的。

### 批量预渲染（把常用曲目提前存到手机）

服务器可以按 catalog 生成清单，一条条派给手机编码，成品**直接落进手机存储**，
把常用难度提前攒到手机里。整个过程不会占用服务器磁盘。

```powershell
# 查进度
curl "http://127.0.0.1:8778/api/batch?token=YOUR_SECRET_TOKEN"

# 启动：紫(5)+白(6)+宴(7)；limit 0 = 不限条数
curl -X POST "http://127.0.0.1:8778/api/batch?token=YOUR_SECRET_TOKEN&slots=5,6,7&limit=0"

# 先跑 30 支试水
curl -X POST "http://127.0.0.1:8778/api/batch?token=YOUR_SECRET_TOKEN&slots=5,6,7&limit=30"

# 停止（当前这条会跑完再停）
curl -X POST "http://127.0.0.1:8778/api/batch?token=YOUR_SECRET_TOKEN&stop=1"
```

行为要点：

- **成品直接写进手机**（`/sdcard/Download/maimai/`），服务器缓存**一个字节都不增加**。
- **自动跳过已经存进手机的条目**（查 `_archived_index.json`），
  所以中断后重新启动会接着往下跑，不会把两千首从头再编一遍。
- **服务器缓存里已有、且手机也已收录的，直接跳过**，不重复搬运。
- 一次只跑一支：入队 → 等「已存手机」通知 → 下一条。轮询 2 秒一次。
- 每条默认超时 `600` 秒，超时记 `failed` 并把它撤出渲染队列。
- `slots` 只认 **2-7 的槽位号**（不是群里敲的 1-5）：
  `5`=紫 `6`=白 `7`=宴。
- 清单是「笛卡尔积」：紫+白+宴意味着**同一首有白谱就出两支**（紫一支、白一支），
  有宴谱的 152 首单独再出一支。

**规模与耗时参考**（Mi 10 Pro 实测，720p/60fps/4 Mbps，含音轨）：

| 范围 | 支数 | 视频总时长 | 手机占用 | 纯编码耗时 |
|---|---|---|---|---|
| 紫 Master (5) | 1779 | 64.5 小时 | 72.2 GB | 约 37 小时 |
| **紫+白+宴 (5/6/7)** | **2106** | **76.0 小时** | **85.0 GB** | **约 43.5 小时** |
| 全部 2-7 | 7437 | 268.7 小时 | 300.4 GB | 约 154 小时 |

单支时长：最短 60 秒 / 中位 134 秒 / 最长 261 秒。编码速度约 **1.7 倍实时**
（11879 全曲 9850 帧 / 164 秒的视频，手机编 94 秒，加音轨再多 4 秒）。

> **手机存储够不够**：实测 465 GB 总量、剩余 400 GB，85 GB 完全放得下。
> 如果只想要「每首一支」，用 `谱面确认` 不写难度那套按需渲染就行，
> 不必批量铺满 —— 批量只适合「想秒回」的常用场景。

> **想重做全部老片**（比如加了音轨之后发现老片都是静音的）：
> 1. 手机上 `rm -f /sdcard/Download/maimai/*.mp4`（音轨缓存 `maimai_audio/` 留着，能复用）
> 2. 服务器上删掉 `cache\mp4\_archived_index.json`（否则会被当成"已完成"跳过）
> 3. 重启机器人，再 `POST /api/batch?slots=5,6,7`

> **跑批量期间手机要保持工作页开着**（可以锁屏、可以切后台，已实测 Worker 不受节流影响），
> 但**标签页不能被系统回收**。而且手机上的 `render_server.py` 必须活着，否则成品存不下来。
> 中断了直接再 `POST` 一次就会接着跑。
> 手机存储不是瓶颈：实测可用 359 GB。

> **批量能不能无人值守跑一夜？** 可以，前提只有三个：
> ① 手机插着电；② Chrome 里的 `worker.html` 标签页没被系统回收（建议在
> Chrome 设置里把这站点加进「不优化」名单）；③ Termux 里的 `render_server.py` 还活着。
> 云服务器的开关机、IP 变化都不影响，因为连接方向始终是手机发起。


### 想看手机工作页在干什么

在手机 Chrome 里直接看页面上的「任务日志」，会实时打印：

```
[18:24:32] → 领取任务 11422 槽5（req rnd_1792146223018_…）
[18:24:50] ✓ 11422_5.mp4 29.3 MB，已上传服务器
```

> 旧版文档里的「电脑端 CDP 远程读取日志」方案已随脚本一并移除（对应 `.mjs` 文件已不存在），
> 看日志就用手机页面上的这份任务日志。

## 五、故障排查

### 群里提示「手机节点还没上线，两步启动：…」

原因：Termux Agent 与渲染工作页**都不在线**（代码里 `is_phone_online()` 与 `is_worker_alive()` 同时为假）。

处理：
1. 确认手机 Chrome 打开着 `worker.html` 工作页（打开一次即可，之后可以切后台）
2. 确认手机的 `render_server.py` 还在跑：手机 Termux 里 `curl http://127.0.0.1:8777/healthz` 有响应
3. 确认手机能出网：手机浏览器打开 `http://YOUR_SERVER_HOST:8778/healthz`
   （打不开就是手机网络问题，或服务器安全组没放行 8778）
4. 看工作页日志有没有 `⚠ 拉取任务失败`

### 群里提示「手机没有这条的预录视频，也检测不到渲染工作页在跑。」

原因：手机 Agent 在线，但既没有这条的预录成品，工作页的 `worker.alive` 也是 `false`。

处理：按提示在手机 Chrome 打开回复里的那条链接（`http://127.0.0.1:8777/worker.html?...`），
页面状态文字变成 `在线待命` 后重发一次命令即可。页面不用一直留在前台。

### 工作页显示「⚠ 当前不是安全上下文」

说明你打开页面的地址不是 `127.0.0.1`/`localhost`。改成
`http://127.0.0.1:8777/worker.html?...` 即可。用手机公网 IP、局域网 IP、
或者用电脑浏览器打开都会出现这句提示 —— 因为 `VideoEncoder` 只在安全上下文里存在。

### 渲染一直不开始 / 进度卡住

- **确认这个标签页还活着**（没被划掉、没被系统回收）。页面可以在后台，编码照跑；
  但标签页一旦被销毁，Worker 也就没了。用 `adb shell dumpsys window | grep mCurrentFocus`
  看不到 Chrome 不代表出错——那是正常的后台状态。
- **同一时刻只能有一个编码任务在跑**。两个 Worker 会互抢手机独占的硬件编码器而全部停滞。
  工作页会自动串行执行队列里的任务，正常使用下不会撞上；`render_queue.pending` 长时间
  大于 1 时再看这一条。
- 早期版本要求「Chrome 必须停留在前台」是因为编码跑在主线程上，会被后台节流（实测精确卡在
  第 5431 帧）。改成 Web Worker 后这条限制已解除，文档里若还有残留说法以本节为准。

### 渲染中途掉线

工作页会记 `⚠ 拉取任务失败：<错误信息>，Ns 后重试`（例如机器人重启期间浏览器报的 `Failed to fetch`）
并指数退避重试（最长 30 秒）。若是机器人重启导致，恢复后会自动接上。

### 视频没有声音

音轨是**手机端自己编的**，服务器只做兜底。所以排查分两段：

**第一段：手机侧（先看这里）**

1. 工作页日志里应该有两行：
   ```
   · 音轨就绪 48000Hz 2ch 88.0s
   · 音轨已写入 4126 帧
   ```
   只有第一行、没有第二行，说明 mux 时出错了；两行都没有就是音轨压根没拿到。
2. 音轨没拿到的常见原因：
   - 日志出现 `音轨下载失败 HTTP 404` → 服务器没把 `audio=` 参数带下来，
     或 `catalog.json` 里这首没有音轨地址
   - 日志出现 `音轨下载失败` 但没有状态码 → 手机连不上音轨源站，或
     `render_server.py` 不是新版（`/audio/<id>.mp3` 会 404）
   - 手机 `/sdcard/Download/maimai_audio/` 里没有对应文件 → 代理没缓存成功
3. 验一下代理本身：手机 Termux 里执行
   ```sh
   curl -s -o /dev/null -w '%{http_code} %{size_download}\n' \
     "http://127.0.0.1:8777/audio/266.mp3?src=https%3A%2F%2Fastrodx-charts.saop.cc%2F2%2F266%2Ftrack.mp3"
   ```
   正常应回 `200 2827647`。回 404 数字很小时是白名单拦了，回 400 是缺 `src` 参数。

**第二段：服务器兜底（手机没编出来时）**

1. 先确认这支到底有没有音轨（命令见上文「正常产物格式」）。
2. 没有的话看服务器日志里有没有 `[PhoneBridge] 补音轨失败（<原因>）`：
   - `no_ffmpeg` → `config.py` 的 `FFMPEG` 路径不对，或那个文件不存在
   - `download_failed` → 服务器连不上 `astrodx-charts.saop.cc`（试试直接 `curl` 一下）
   - `no_audio_url` → 这首在 `catalog.json` 里没有音轨地址（极少数条目）
   - `mux_failed` → ffmpeg 执行报错，日志里带 `detail={...}` 和 stderr 前 300 字
3. 兜底失败**不影响发群**，成片会以无声视频入库。修好原因后把
   `cache\mp4\<id>_<diff>.mp4` 删掉重新点一次即可（手机上的权威副本还在，
   不会重渲染，只会重新走一趟回传）。

### 时长明显偏短（例如 2:44 的曲子只有 5 秒）

历史成因有两类，都已经被处理掉：

- 早期的 `recorder.html` 实时录制方案会被系统节流打断，产出几秒的残片（该方案已删除，
  现在是逐帧离线编码，产物时长天然等于谱面时长）。
- 手工测试、传输中断等留下的**短测试片**堆在手机预录库或服务器缓存里，被旧代码
  （只判断文件大于 1 KB）当成全曲成品发了出去。

为此服务器现在有**两道时长校验守门**（`video_verify.py`，权威时长取自 `data/catalog.json`
的 `difficulties[].duration_ms`）：

1. **接收上传时**（`POST /upload`）：落盘前校验，不合格直接返回 HTTP 422 不入库，
   并把等待者标成「渲染失败」（群收到的是「手机回传的视频没通过完整性校验」提示，
   同时自动转去现场渲染，不会静默等到超时）。
   这一道是 **fail-closed**：上传必须带齐 `chart_id` 与 `diff`（手机端 `encoder-worker.js`
   一直都会带），查不到权威时长就拒收，绝不「查不到就放行」。
2. **读取缓存时**（`get_cached_mp4`）：不合格的移入 `cache/mp4/rejected/` 并记日志，
   然后继续往下走流程 —— 只要手机节点在线（Termux Agent 或渲染工作页任一），
   就会自动转去现场渲染；如果手机整个离线，用户会收到「手机节点还没上线」的提示。
   这一道是**宽松**的：环境异常（缺 ffprobe、catalog 读不到）时放行，避免整库缓存被误隔离。

判定区间为「实际时长 ÷ 期望时长 ∈ [0.75, 1.35]」，校验结果写在同名的 `.mp4.meta.json` 里。
实测正常全曲比值约 `1.017`，而 10 秒残片只有 `0.062`，会被拒绝。

正常产物格式（手机端自己编好音轨之后）：

```
0,h264,video    profile=High  720x720  r_frame_rate=60/1
1,aac,audio     48000 Hz  2 ch  128 kbps
nb_frames=5381  duration=89.683333
```

`nb_frames` 应约等于 `时长 × 60`，可以据此核对。
音轨的长度一般比画面略短一点点（音源本身比谱面短），这是正常的 ——
播放器会停在最后一个画面，不会黑屏。

> 检查某支成片有没有声音：
> ```
> C:\ffmpeg-9.0.2-essentials_build\bin\ffprobe.exe -v error ^
>   -show_entries stream=index,codec_type,codec_name -of csv=p=0 ^
>   cache\mp4\11151_5.mp4
> ```
> 出现 `1,aac,audio` 就是有音轨；只有 `0,h264,video` 说明这支没声音
> （老片，或音轨那一步失败过），删掉它重新点一次即可。

> 若你确实要放行一个时长远低于预期的视频（例如只想测试前 10 秒），
> 去 `cache/mp4/rejected/` 里找被隔离的文件，或把 `video_verify.py` 里的 `MIN_RATIO` 调小。

### 失败文案速查（全部与 `mai_preview.py` 逐字一致）

| 群里收到的原文 | 含义 / 处理 |
|---|---|
| `曲 {id} 没有难度信息，这单做不了。` + `可用：…` | 该曲目录里定不出难度，按第二行给出的选项重发 |
| `谱面确认失败：{…}` | 参数不合法，常见如 `无法识别的难度「x」。可用：1=绿 2=黄 3=红 4=紫 5=白，宴写「宴」。` |
| `谱面确认出错了，已记日志，稍后再试。` | 未预期异常，看 HoshinoBot 根目录的 `log\error.log` |
| `手机节点还没上线，两步启动：…` | 见上文第一张处理卡 |
| `手机没有这条的预录视频，也检测不到渲染工作页在跑。…` | 按回复里的链接打开工作页 |
| `服务器没有缓存，正在向手机调预录视频…` | 正常中间态，不是错误 |
| `手机没预录这条，转现场渲染：…` | 正常中间态，不是错误 |
| `手机渲染超时。看一眼工作页上的任务日志，然后重试一次。` | 超过 `PHONE_RENDER_TIMEOUT_S`（默认 900 秒） |
| `手机渲染到一半掉线，检查工作页和网络后重试。` | 回传前手机失联 |
| `手机端编码失败，看一眼工作页上的任务日志。` | 浏览器编码报错 |
| `手机渲染失败（{reason}），稍后再试。` | 其他失败原因 |
| `调取过程中手机 agent 掉线了，检查 Termux 脚本是否还活着。` | 预录阶段 Agent 断连 |
| `手机回传的视频没通过完整性校验，已丢弃。` + `多半是录制中途被打断…` | 手机确实传回了文件，但时长对不上（`too_short`/`too_long`/`no_reference`），已隔离；服务器同时转去现场渲染 |
| `向手机调取预录视频时出错，稍后再试。` | 预录请求本身出错 |
| `预录视频没调到（{reason}），稍后再试。` | 预录没命中且现场渲染也没开（`PHONE_RENDER_ENABLED=False`） |
| `视频没发出去（协议端可能不支持直发视频）。` + 本地文件路径 | `file:///` 与 base64 两次发送都失败的兜底文案 |

## 七、性能参考（Mi 10 Pro 实测）

| 项目 | 数值 |
|---|---|
| 单帧渲染耗时 | 0.9 ms（约 1000 fps 上限，渲染不是瓶颈） |
| 全曲 164 秒 / 9850 帧 | 约 86 秒完成（≈ 1.9× 实时） |
| 其中渲染 | 11.4 秒 |
| 其中提交编码 | 7.7 秒 |
| 720p/60fps 全曲文件 | 30–55 MB |
| 编码格式 | H.264 High Profile / yuv420p + AAC 48k 双声道 128kbps |
| 手机端编音轨 | 约 **4 秒/支**（4126 帧 AAC，与画面编码并行不起来，串在前面） |
| 手机端下载音轨 | 2–3 MB / 约 5–8 秒（走本机代理，之后命中缓存是 0.02 秒） |
| 服务器兜底补音轨 | 约 **4 秒/支**（`-c:v copy`，画面不重编码）；手机已带音轨时直接跳过 |

瓶颈在 H.264 硬件编码吞吐，不在渲染引擎。如果嫌慢，可以降 `px` 到 540；如果嫌画质不够，可以升到 1080（注意 1200 以上会超出 Level 4.0 上限而不可用）。

## 八、附：反方向通道（gost 8443 中继）

当前架构**不需要**任何反向隧道，因为所有连接都是手机主动出站。
但服务器上确实跑着一个 gost relay（`C:\gost3\gost.exe`，监听 `8443`，
由计划任务 `gost-relay-task.xml` 开机拉起），服务器借此借用手机的网络出口上网。
知道它的行为有用：

| 问题 | 答案 |
|---|---|
| 多个通道共用 8443 会互相挤掉吗 | **不会**。relay 按「服务器侧绑定的目标端口」区分通道，天然多路复用 |
| 当前用了几条 | 1 条：`127.0.0.1:17890`（服务器经手机代理出网）。实测这条通道访问百度正常 |
| 想再加一条怎么做 | 在服务器上跑 `gost -L tcp://127.0.0.1:<新端口> -F relay://<用户>:<密码>@127.0.0.1:8443`，**端口不能与已占用的重复** |
| 能绑 8778 吗 | **不能**。8778 已被 aiohttp 通信桥占用，绑上去只会失败 |
| 需要给「服务器→手机 8780」开反向通道吗 | **不需要**。落盘上报是手机主 `POST` 到公网 8778，方向是手机→服务器 |

> 实测验证过的结论：relay 可以同时承载多条通道，只要服务器侧绑定的端口各不相同；
> 有意用 `18779` 做过建链实验，与现有的 `17890`、`8778` 均无冲突，
> 实验后已清理，无残留进程与端口。
